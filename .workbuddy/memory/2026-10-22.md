**技术选型**

## 数据存储方案（用户追问，已确认现状与选型）

**现状：100% 本地** `wx.setStorageSync`，共 6 个 key：
`wm_books` / `wm_words_<id>` / `wm_wrong_<id>` / `wm_settings` / `wm_stats`。

**实测容量（用 estimateBytes 跑出来的真实数字）**
- 100 词 ≈ 6KB；688 词 ≈ 44KB；3000 词 ≈ 195KB
- 3 本 × 688 词 + 200 错词 + 统计 = **176KB**
- 结论：微信 10MB 上限根本碰不到，容量兜底属防御性设计。
- 真正的痛点只有三个：换机/卸载丢失、微信清缓存被清、多设备不同步。

**云端方案对比（已核实官方能力）**
1. **微信云开发（推荐）**：`wx.cloud.init()` + `wx.cloud.database()`。
   关键优势：**不需要 wx.login / code2Session**，云函数里 `cloud.getWXContext()` 直接拿 openid。
   数据库权限默认「仅创建者可读写」，天然符合按用户隔离。
2. **自建服务器**：`wx.login()` → code → 服务器 → `auth.code2Session` → openid + session_key。
   注意 session_key 绝不能下发到小程序端。需备案域名 + 运维。
3. **保持本地 + 导入导出备份**：零成本，但不解决自动同步。

**重要事实**：`wx.getUserProfile` 已回收，wx.login 拿不到昵称头像；
本项目只需要 openid 做数据归属，**不需要**头像昵称/手机号（后者还是收费能力）。

**上云的连带成本**：隐私保护指引要补充「收集与存储用户学习数据」的说明。

## 第三轮迭代（同日上午）· 本地 / 云端双模式可切换

用户要求「本地存储和云存储做成后台可切换的模式」。已实现并测试。

### 架构决策（关键，别推翻）
**本地优先 + 云端异步双向同步**。起因：业务代码 25 处 storage 调用**全是同步**，
改异步要动所有页面。所以约定：
- **读永远走本地**（同步，业务代码零改动）
- **写先落本地，再异步推云**（storage 内部钩子触发，页面无感知）
好处：断网照样能背，不会出现转圈等网络。

### 新增文件
- `utils/cloud.js`：云开发封装。**第一契约是永不因云环境缺失而崩溃**——
  无 SDK / 未开通 / 网络断开 / env 填错，一律静默降级（返回 null / false，不抛异常）。
  `CLOUD_ENV` 留空时会尝试「默认环境」初始化（账号只有 1 个环境时免配置）。
  集合 books/words/wrong/stats/settings，权限「仅创建者可读写」。
  **整本词库存一条文档**（数组内嵌），把调用次数压一个数量级（计费瓶颈是调用次数）。
  本地缓存云端 `_id`（`wm_cloudmap`），更新走 1 次调用，失败回退「先查再增」。
- `utils/sync.js`：同步引擎。dirty 键持久化（`wm_dirty`），重启后未推成功的继续推。
  防抖 900ms 合并连续改动。冲突按 `updatedAt` 较新者为准。
  策略：keep-local / keep-cloud / merge（两端都有数据时由 UI 弹窗让用户裁决）。
- `pages/data/data`：存储方式切换 UI（两个大卡片 + 状态 + 概览 + 立即同步 + 删除云端数据）。

### storage.js 的接入方式
`write()` 类操作后调 `notify(key)`，key 形如 `book:<id>` / `wrong:<id>` / `stats` / `settings`。
**延迟 require 打破循环依赖**（storage ↔ sync 互相只在运行时取对方完整导出）。
新增导出 `saveBooks` / `saveWrongList` / `saveStats`（云端合并回写需要）。
注意 `saveStats` 刻意不 notify —— 拉下来的数据不该再被标脏推回去。

### 本轮修掉的三个真 bug（测试逼出来的）
1. **pushDirty 误清脏键**：cloud 方法失败返回 `false` 而非 reject，`Promise.all` 仍 resolve，
   导致失败项的 dirty 被删除 → 本地有、云端无，且永不重试（永久丢数据）。
   改为逐项收集 `key -> ok`，只删成功的。
2. **断网检测从未生效**：`cloud.usable()` 里写的是 `wx.getNetworkType ? ...getNetworkTypeSync()`
   —— 判断异步版、调用同步版，真机上永远认为有网。改为 `typeof wx.getNetworkTypeSync === 'function'`。
3. **离线状态反馈延迟**：只在防抖窗口结束后才变灰。改为 `touch()` 里立即判网络并置 `unavailable`。

## 架构复审（用户问「这样合理吗」）· 发现的设计缺陷

结论：**方向合理（本地优先 + 异步推云），但「冲突解决」层是半成品，且恰好错在最值钱的两类数据上。**

### 缺陷 1：stats 用「整对象覆盖」，但它是累加器（严重）
`storage.recordStats()` 是 `+=` 语义（`totalMatched += matched`、`days[key].matched += ...`）。
`sync.applyCloud()` line 301 只在 `force || !getTs('stats')` 时才采用云端 —— 等于**统计基本单向**，
多设备各玩各的再联网，一端累计量直接被另一端覆盖，连续天数也会回退。
正解：`days` 按日期 key 逐项合并（同日取 max 而非累加，防重复计），
`totalXxx` / `streak` / `bestStreak` 全部由 `days` **派生重算**，不再独立存储。

### 缺陷 2：错词本用「整列表覆盖」，但它是 per-word 计数器（严重）
`markWrong/markRight` 维护的是每条 `{en, wrong, right, mastered}` 的计数器。
`applyCloud` line 289-298 条件为 `force || !localTs || list.length > 0` ——
云端非空就整体覆盖本地。后果：A 机上某词已「连续答对 2 次毕业」，
B 机上昨天错了一次（云端列表更长），一拉就把毕业的词**复活**，且 wrong 计数被回退。
另注：line 292 `const cloudTs = 0` 是未完成的占位（`void cloudTs`），当时就是权宜。
正解：按 `(bookId, en)` 逐条合并 —— `wrong` 取 max、`right` 取 max、`mastered` 由 right 阈值推导。

### 缺陷 3：settings 无条件覆盖 + 可能推拉循环
`applyCloud` line 308 每次拉都 `saveSettings(s)` 无条件覆盖本地。
若本地刚改设置还没推（防抖 900ms 内）或离线改过，会被云端旧值回滚。
另：`saveSettings` 会 `notify` → `touch('settings')` → 再标脏推一次，存在循环风险。
正解：合并回来的写操作必须走「静默写」（不 notify、不标脏）。

### 缺陷 4（产品层面）：不该让学生做「本机 / 云端」的技术决策
用户是中小学生。合理默认应是 **auto**：有云就用云、没云自动纯本地，无需用户理解。
手动开关应降级为「高级设置」。

### 风险窗口的诚实评估
上述 1/2 只在「**两台设备都离线玩过，再先后联网**」时发作。单人单机、或换机首次拉取
（本地为空）的场景下 newer-wins 是正确的。所以是真实缺陷但不是天天炸，
优先级取决于是否允许多设备。

### 最大的未验证项
148 项测试**全部是 Node 桩**，零真机验证。真机上未验证：
wx.cloud 权限规则实际生效、chooseMessageFile、AudioContext 在 iOS 静音模式下、
TTS 域名白名单、云环境未开通时的降级表现。发布前必须真机跑一遍。

## 第四轮（同日）· 按复审结论修复合并缺陷

用户确认「先动手修改」。已全部改完并测试。

### 修复 1：学习统计改为「按设备分桶的 G-Counter」
**根因**：`recordStats` 是累加语义，整对象覆盖会丢数据；对汇总值直接相加会在
每次同步中无限膨胀（B 拉到 A 的 30 → 本地 50 → 推上去 → A 再拉 50 + 自己 30 = 80…）。

**方案**：`days[key].by = { 设备ID: {matched,games,wins,seconds} }`，
`matched/games/wins/seconds` 变成由 `by` 求和的**派生值**；
`totalXxx` / `streak` 也都由 `days` 派生（`rollupStats`）。
同一设备重复合并取 max（防重放），不同设备求和。
- 新增 `utils/storage.js`：`getDeviceId()`（存 `wm_device_id`）、`emptyDay()`、
  `rollupDay()`、`migrateDay()`（旧格式迁移）、`rollupStats()`、`mergeStats()`。
- 旧格式（无 `by`）迁移：本地归本机 id，云端归 `LEGACY_OWNER='legacy'`，两边不互相顶掉。
- 实测：本机 10 + 他机 5 = 15；同一 remote 重复合并仍是 15（不膨胀）；本机继续背 → 20。

### 修复 2：错词本逐词合并
新增 `storage.mergeWrongList(bookId, remoteList)`：
- `wrong` 累计次数 → 取 max
- `right` 连续答对（答错会清零，非单调）→ 按 `at` 取**更近的一侧**
- `mastered` 由 `right >= MASTER_THRESHOLD` 派生，保证状态自洽
- 只在一端出现的词直接保留
效果：本机已毕业的词不会被另一端的旧列表复活；但另一端**更晚**的答错仍能把它拉回错词本。

### 修复 3：设置静默落地 + 脏键保护
- 新增 `saveSettingsQuiet()` / `saveWordsQuiet()`：只写本地、不 notify。
  避免「拉 → 标脏 → 又推」的循环调用。
- `applyCloud` 里加 `isDirty('settings')` 判断：本机有未推送的改动时**不**用云端覆盖，
  否则会把用户刚改的设置回滚。

### 修复 4（产品）：默认 auto，不让学生做技术选择
- sync 模式从 `local | cloud` 改为 **`auto | local`**（旧存的 'cloud' 自动归并为 auto）。
  auto = 能连云就同步、连不上安静退回本机，用户零感知。
- 新增 `cloudReady` 运行时标志与 `active()`（取代散落的 `mode !== 'cloud'`）。
- 新增 `watchNetwork()`：启动时无网会导致 cloudReady 永久 false，
  监听 `wx.onNetworkStatusChange` 在有网时重试 `cloud.init()`，不必重启小程序。
- `pages/data` UI：两张卡改为「自动备份（推荐）/ 只存本机」，加「推荐」徽标；
  状态文案改「已备份到云端」「云端暂不可用，已存本机」。
- 首页脚注同步改为按 cloudOn 显示。
